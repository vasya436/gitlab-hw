## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

# Решение: GitHub + GitHub Actions + self-hosted Runner'ы

## Состав

- **GitHub (облачный)** - хранение исходного кода: репозиторий на каждый сервис,
  pull request'ы, управление доступом (teams, branch protection).
- **GitHub Actions** - непрерывная интеграция и поставка: сборка, тесты, деплой.
- **Self-hosted Runner** - агент сборки на собственном сервере (Docker executor,
  свои докер-образы).

## Как закрываются требования

| Требование | Как решается |
|---|---|
| Облачная система | GitHub SaaS (github.com) |
| Git, репозиторий на каждый сервис | один GitHub repository = один сервис |
| Сборка по событию из VCS | триггеры: `push`, `pull_request`, теги, `schedule` (cron) |
| Сборка по кнопке с параметрами | `workflow_dispatch` + `inputs` (запуск вручную с параметрами) |
| Настройки для каждой сборки | `env`, `outputs`, условия `if`, окружения (`environments`) |
| Шаблоны конфигураций сборок | reusable workflows (`workflow_call`) + `include` через матрицы |
| Безопасное хранение секретов | GitHub Secrets (зашифрованные, masked), переменные окружений |
| Несколько конфигураций из одного репозитория | несколько workflow-файлов + `matrix` |
| Кастомные шаги | `run:` - произвольный shell-скрипт на любом шаге |
| Собственные докер-образы | `runs-on` + `container:` или `jobs.<id>.container.image` / GHCR |
| Агенты на своих серверах | self-hosted runner (`runs-on: self-hosted`) |
| Параллельные сборки | параллельные jobs, матрицы `strategy.matrix` |
| Параллельные тесты | разбиение тестов по jobs / `matrix` + `parallel` |

# Решение: Loki + Promtail + Grafana

## Состав

- **Promtail** - агент на каждом хосте: читает логи из файлов и **stdout**
  контейнеров (Docker/Kubernetes, journald, `var/log`), парсит и шлёт дальше.
  Минимальные требования к приложениям - не нужен ни SDK, ни изменение кода.
- **Loki** - центральное хранилище логов: индексируются только метки
  (`service`, `host`, `env`), сами записи хранятся сжатыми блоками -
  дёшево и просто.
- **Grafana** - пользовательский интерфейс: поиск, фильтрация, дашборды,
  доступ разработчикам (локальные пользователи или интеграция с OAuth/LDAP).

## Как закрываются требования

| Требование | Как решается |
|---|---|
| Сбор со всех хостов в центральное хранилище | Promtail на каждом хосте → Loki |
| Минимум требований к приложениям, сбор из stdout | приложения пишут в stdout/stderr, Promtail читает сам |
| Гарантированная доставка | Promtail хранит позицию чтения и буферизует неотправленное на диске; при недоступности Loki - ретраи, после восстановления досылает |
| Поиск и фильтрация | язык запросов LogQL: фильтры по меткам, по содержимому строки, regex |
| UI с доступом разработчиков | Grafana Explore: веб-доступ, пользователи/команды с разграничением прав |
| Ссылка на сохранённый поиск | сохранённые запросы (Saved queries) и Explore-панели, URL запроса копируется и передаётся |

## Взаимодействие

1. Приложение пишет в stdout/stderr.
2. Promtail на хосте читает лог и добавляет метки (`service`, `host`, `env`).
3. Promtail отправляет записи в Loki (центральное хранилище).
4. Разработчик ищет в Grafana (Explore) по меткам и тексту, например:

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

# Решение: Prometheus + Grafana

## Состав

- **Prometheus** - центральное хранилище метрик: сам опрашивает (pull) эндпоинты
  `/metrics` по расписанию, хранит временные ряды, считает агрегации на лету
  языком PromQL.
- **node_exporter** - агент на каждом хосте: отдаёт метрики CPU, RAM, дисков, сети.
- **cAdvisor** - метрики потребления ресурсов каждого контейнера/сервиса
  (CPU, RAM, I/O, сеть).
- **Экспортеры и `/metrics` приложений** - сервисные метрики: RED
  (rate, errors, duration), счётчики запросов, глубина очередей и т.п.
- **Grafana** - UI: запросы через PromQL, панели, дашборды, доступ команд.

## Как закрываются требования

| Требование | Как решается |
|---|---|
| Сбор метрик со всех хостов | node_exporter на каждом хосте, Prometheus опрашивает их по конфигу |
| Ресурсы хостов: CPU, RAM, HDD, Network | node_exporter отдаёт всё это из коробки |
| Ресурсы каждого сервиса | cAdvisor: метрики по каждому контейнеру отдельно |
| Специфичные метрики сервисов | сервисы экспортируют свои метрики через `/metrics` (клиентские библиотеки Prometheus), плюс exporters для БД/брокеров |
| UI с запросами и агрегациями | Grafana Explore + PromQL: `sum(rate(...))`, `by (service)` и т.д. |
| UI с настраиваемыми панелями | Grafana дашборды: графики, гейджи, таблицы, переменные, алерты |

## Взаимодействие

1. Сервисы и node_exporter отдают метрики по HTTP (`/metrics`).
2. Prometheus по расписанию забирает их (pull-модель) и хранит как временные ряды.
3. Grafana запрашивает данные через PromQL и рисует дашборды.
4. Алерты - через Alertmanager (опционально).

## Обоснование

- **Промышленный стандарт** для микросервисов: pull-модель проста и надёжна -
  если Prometheus не смог забрать метрики, это само по себе сигнал о проблеме.
- **Готовая экосистема**: node_exporter, cAdvisor, exporters для PostgreSQL,
  Redis, RabbitMQ и т.д. - почти всё есть из коробки, сервисам достаточно
  выставить `/metrics`.
- **Минимум нагрузки на приложения**: не нужно пушить метрики, просто открыть
  HTTP-эндпоинт.
- **Мощный язык запросов**: PromQL покрывает и простые графики, и сложные
  агрегации (rate, гистограммы, квантили).
- **Grafana - де-факто стандарт**: бесплатный, гибкие дашборды, готовые шаблоны
  сообщества, общий UI с логами (Loki) — тот же инструмент, что выбран в задаче 2.

Альтернативы (кратко)
Zabbix - силён в проверках доступности и агентной модели, но слабее в метриках приложений и PromQL-подобных запросах; UI старомодный.
InfluxDB + Telegraf - хорошая связка, но PromQL и экосистема Prometheus для микросервисов удобнее.
VictoriaMetrics - совместимая с Prometheus замена хранилища, стоит рассмотреть при больших объёмах данных.
Итог
Prometheus + node_exporter + cAdvisor + Grafana закрывают все требования из коробки, интегрируются с логами из задачи 2 (тот же Grafana) и дают единый стек: метрики + логи + алерты + дашборды.
