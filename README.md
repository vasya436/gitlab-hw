# Домашнее задание к занятию «Микросервисы: принципы» - Василий Ткаченко

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.

## Задача 1: API Gateway 

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

На рынке есть несколько зрелых open-source решений, которые закрывают все три требования:

| Возможность | NGINX | Kong | Traefik | Envoy | HAProxy |
|---|---|---|---|---|---|
| Маршрутизация по конфигурации | да (конфиг-файлы) | да (файл / REST / БД) | да (файл / метки Docker, K8s) | да (YAML / xDS) | да (конфиг-файлы) |
| Проверка аутентификации (JWT, ключи API, OAuth2) | частично (нужен Lua/njs) | да, из коробки (JWT, OAuth2, ключи — плагины) | да (мидлварь, плагины) | да (JWT-фильтр, ext_authz) | частично (нужен Lua/SPOE) |
| Терминация HTTPS | да | да | да (автополучение сертификатов Let's Encrypt) | да | да |
| Динамика конфигурации без перезапуска | нет (reload) | да | да | да | ограниченно |
| Сложность эксплуатации | низкая | средняя | низкая | высокая | низкая |
| Экосистема плагинов | ограниченная | богатая | средняя | растущая | ограниченная |

## Выбор

**Kong.**

### Обоснование по трём требованиям

1. **Маршрутизация** - гибкие правила по путям, хостам, заголовкам; конфиг хранится
   в декларативном YAML или через Admin API, меняется без перезапуска.
2. **Аутентификация** - готовые плагины JWT, OAuth2, API-ключи, basic auth:
   не нужно писать ничего своего.
3. **HTTPS-терминация** - встроенная, сертификаты подключаются в конфигурации.

### Альтернатива

Если инфраструктура простая и лишний сервис поднимать не хочется -
**NGINX + Lua (njs)**: все три требования закрываются, эксплуатация проще,
но аутентификацию придётся дописывать самому.

## Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:
- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

## Сравнение брокеров

| Возможность | RabbitMQ | Kafka | NATS JetStream | Redis Streams |
|---|---|---|---|---|
| Кластеризация для надёжности | да (кворумные очереди, зеркалирование) | да (репликация партиций) | да (RAFT-консенсус) | да (Sentinel / Redis Cluster) |
| Хранение сообщений на диске | да (при durable-очередях) | да (всегда, log на диске) | да (файловое хранилище) | да (AOF/RDB, ограниченно) |
| Высокая скорость | средняя (~50K msg/s) | очень высокая (~1M msg/s) | очень высокая | высокая (~100K msg/s) |
| Различные форматы сообщений | да (JSON, XML, protobuf, любые байты) | да (байты, любые сериализации) | да (байты, protobuf) | да (строки/байты) |
| Права доступа к потокам (топикам) | да (vhost, ACL на обменники и очереди) | да (ACL на топики) | да (accounts/permissions) | да (ACL по ключам, грубее) |
| Простота эксплуатации | высокая (простой веб-интерфейс) | средняя (нужен ZooKeeper/KRaft, много настроек) | высокая (один бинарник) | высокая, но хранение слабое |

## Выбор

**RabbitMQ.**

### Обоснование по требованиям

1. **Кластеризация** - кворумные (quorum) очереди реплицируются между нодами,
   брокер переживает отказ узла без потери сообщений.
2. **Хранение на диске** - durable-очереди и persistent-сообщения пишутся на диск,
   доставка не теряет данные при перезапуске.
3. **Скорость** - ~50K сообщений/с на узел достаточно для типичных сервисов;
   узкое место можно масштабировать добавлением узлов.
4. **Форматы** - RabbitMQ передаёт любые байты: JSON, XML, protobuf и т. д.,
   плюс гибкая маршрутизация (обменники, routing keys).
5. **Права доступа** - granular ACL: пользователи и vhost'ы разграничивают доступ
   к конкретным обменникам и очередям (потокам).
6. **Эксплуатация** - установка из коробки, понятная веб-консоль, огромное
   сообщество и документация.

### Почему не Kafka

Kafka быстрее, но это избыточно для задачи: её эксплуатация заметно сложнее
(партиции, консюмер-группы, KRaft), а модель хранения рассчитана на потоковые
события и долго хранящиеся логи. Если бы требовалась пропускная способность
в сотни тысяч сообщений/с и ретейн данных - выбор был бы в пользу Kafka.

### Когда рассмотреть NATS JetStream

Если сервисы - маленькие микросервисы с простыми сценариями и нужна минимальная
нагрузка на инфраструктуру (один бинарник, очень высокая скорость) - NATS
JetStream тоже закрывает все требования и проще Kafka.
